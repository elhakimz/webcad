## What this project is

This is **WebCAD** — a full browser-based 2D/3D CAD application written in TypeScript. It blends an AutoCAD-style drafting environment (layers, entities, a command line, snap/grid/ortho) with an OpenSCAD-compatible parametric scripting system, powered by OpenCascade.js running as a WASM Web Worker for all B-Rep geometry. It's an ambitious, impressive project.

---

## Strengths

**Clean command interface.** The `Command` interface (`onPoint`, `onInput`, `getPreview`, `getPrompt`, `getDynamicInput`, `getOptions`) is well-designed. All 78 command classes are consistent and can be tested in isolation, which the 41 test suites take good advantage of.

**Handler dispatch pattern.** `ActionHandler` with `canHandle` / `handle` cleanly separates action processing from the orchestrator. This is the right architecture.

**SCAD pipeline is well-layered.** Lexer → Parser → AST → `ScadEvaluator` → `CsgExecutor` → OCC is a proper compiler pipeline. The off-main-thread OCC execution design is correct and important for browser responsiveness.

**WASM memory management.** `OCCWorker.ts` has careful `shapeCache` cleanup with try/catch `delete()` calls and the `detachShape` helper. This is the kind of detail that prevents browser crashes.

**Spatial indexing.** The Quadtree on `Document` for entity queries is the right call at CAD scale.

**Good test coverage for core logic.** Commands, snap engine, selection, coordinate parser, math utils, and the SCAD system all have tests.

## Issues and recommendations

### 1. `App` is a God Object (~1400 lines)

`app.ts` handles input routing, entity management, 2D/3D mode switching, grip interaction, selection boxes, command dispatching, gizmo management, drafting state, and a dozen UI callbacks — all in one class. It's the single biggest maintenance risk. The suggested split:

- `InputRouter` — mouse/keyboard event dispatch, drag detection, grip logic
- `SelectionManager` — selection state, box selection, 3D sub-entity picking
- `EntityManager` — `addEntity`, history recording, viewer sync
- `App` itself becomes a thin coordinator holding references to these services

### 2. The `instanceof` chain on line 1162

```ts
if (result instanceof Line || result instanceof Circle || ... || (result as any).type === "Solid3D" || result instanceof Solid3D)
```

This checks 14+ concrete types to ask one question: *"is this an entity?"* The answer is already in the type system — `Entity` is the abstract base. The fix is to move the check to `result instanceof Entity`. The dual `(result as any).type === "Solid3D" || result instanceof Solid3D` pattern repeating in several places (lines 376, 1162, 1224, 1322) signals that deserialized `Solid3D` objects sometimes don't survive `instanceof` checks — likely because they're reconstructed as plain objects during persistence round-trips. `EntitySerializer.deserialize` should ensure it returns a proper `new Solid3D(...)` instance every time.

### 3. `Viewer.ts` at 3419 lines

This file renders all 20+ entity types, handles preview rendering, camera control, grid, cursor, selection highlighting, and 3D mode. It's too large to reason about safely. A natural split already exists in the codebase (note `GridRenderer` and `CursorRenderer` are already extracted) — continue that pattern:

- `EntityRenderer` — per-type rendering logic (the big `if/else` chains)
- `PreviewRenderer` — preview object rendering
- `Viewer` — scene setup, camera, input forwarding, render loop

### 4. `ScadEvaluator` accumulates module definitions across runs

`this.modules` and `this.functions` are instance-level `Map`s on `ScadEvaluator`, which is reused via `ScadManager`. Module definitions from previous scripts accumulate — if a module named `hole` exists in script A and the user switches to a script B without that module, old definitions persist. Add `this.modules.clear(); this.functions.clear();` at the top of `evaluate()`.

### 5. Non-determinism in `HullCommand`

The convex hull implementation applies `Math.random() * 1e-7` jitter to all input points for numerical stability. This means identical geometry inputs can produce slightly different hull outputs on re-evaluation, which could cause geometry flicker or inconsistent undo states. Use a deterministic perturbation (e.g. index-based offsets) instead of random noise.

### 6. 43 `console.log` calls in production code

Scattered debug logging will appear in every user's browser console. Replace with a toggleable logger (`const log = DEBUG ? console.log : () => {}`) or remove.

### 7. `CommandAction` is a single 70-value string union with all-optional payload fields

```ts
type CommandAction = { action: 'finish' | 'close' | 'delete' | ... ; id?: string; ids?: string[]; entity?: Entity; ... }
```

Every field is optional, so the TypeScript compiler can't tell you if you forgot `radius` on a `fillet` action. Consider discriminated union subtypes, or at minimum document which fields each `action` value requires via JSDoc.

### 8. Missing `children()` in SCAD evaluator

The `TODO` comment in `Evaluator.ts` notes that `children()` calls in user-defined SCAD modules aren't implemented. This is a significant OpenSCAD compatibility gap that prevents common library patterns from working.

### 9. `as any` casts for command capability checks

Patterns like `(active as unknown as any).setEntity(entity)` at line 1100 bypass the type system because the active command's concrete type isn't known at the call site. The existing `HasSetEntity`, `HasBasePoint`, `HasUpdateSketch` etc. interfaces are the right solution — the problem is the checks aren't being applied before the cast. Use `instanceof` checks against these interfaces (`if ('setEntity' in active)`) or narrow via the interface types.

### 10. No undo support for SCAD-generated entities

When SCAD execution creates entities, they're added to the document but not via `recordAdd` — so `undo()` won't remove them. SCAD runs should either integrate with `HistoryManager` or manage their own entity set that gets fully replaced on each re-run.
